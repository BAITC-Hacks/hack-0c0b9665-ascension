## Конфликт данных, который нужно разрешить вместе

У Данияра `src/complaints/` хранит JSON-реестр, внешние ID `C-…`, статусы `new/in_progress/resolved/rejected`, private tracking tokens, `X-Admin-Token`, Telegram file IDs и уведомления из своего PATCH.

У кабинетов `src/desk/` хранит SQLite, числовые ID, дополнительные этапы `review/clarification/work`, integer version, cookie auth, поручения/группы, BLOB-фото, публичные ответы, токены с ротацией и привязанные к циклу решения публикации.

HTTP-пути могут существовать рядом, но два реестра не дают общего сценария. Согласовать с владельцем Cloudflare-адаптации один авторитетный реестр и совместимый адаптер. Сохранить внешние ID, категории, стадии, конкурентные правки, старые ссылки и фото; повтор webhook не должен создавать дубль. Действие в desk/akim/resident должно изменять то же обращение и при необходимости создавать уведомление боту. Не выбирать новое хранилище или переносить живые данные независимо от уже начатой работы Данияра/Азамата.

## Порядок общей публикации

1. Получить в issue #18 актуальную ветку/владельца Cloudflare-адаптации и согласовать контракт реестра. Секреты в обсуждение не отправлять.
2. Собирать готовые SHA от локальных задач. Git-операции в общей папке выполняет один согласованный исполнитель; до commit на короткое время замораживать записи остальных. Не использовать массовый stage чужих незавершённых файлов без согласованного checkpoint.
3. Интегрировать в отдельной ветке/worktree от свежего main. Данияровы `app/index/styles/server` пересекаются с локальными: разрешать смысловые конфликты с сохранением карты, основного интерфейса, policy panel, comparison export, общей библиотеки сценариев и новых кабинетов. Не переносить старый локальный каталог поверх main целиком.
4. Проверить серверные тесты и полный маршрут: Telegram/web → одно обращение → кабинет → поручение/решение → уведомление → отзыв жителя → повторное рассмотрение. Проверить права, фото, дубли, старые токены и одновременное редактирование. Отдельно проверить карту, A/B, библиотеку и мобильный экран.
5. Единственный релиз выполняет согласованный владелец существующего Cloudflare-доступа: сначала сборка dry-run, затем deploy проверенного SHA. Сохранить действующие bindings, AI budget, секреты и постоянные данные. Новые платные ресурсы или альтернативный домен в эту договорённость не входят.
6. Проверить фактические страницы и API на целевом адресе; записать SHA, deployment ID и результаты в issue #18. Commit/push/dry-run и localhost не обозначать опубликованным сайтом.

Публикация уже разрешена пользователем. На этом компьютере доступ Cloudflare не обнаружен; рабочий канал GitHub доступен через существующую Git-авторизацию. Отсутствие доступа и незавершённая общая адаптация являются техническими блокерами, а не запросом повторного разрешения на релиз.
