# План сайта с жалобами из Telegram

Дата: 23 сентября 2026. Это предложение по следующему этапу, а не отчёт о реализованных функциях или назначенных карточках Trello. Основание — текущие `src/server.js`, `public/`, README и интеграционный контракт.

Данияр отвечает за Telegram-бота — подтверждено пользователем. Остальное распределение ниже предлагается: Азамат — сервер и интеграция, Алишер — интерфейс обращений. Старые поручения Данияру в roadmap относятся к предыдущему этапу. Перед изменением общих файлов нужно учесть уже работающую задачу карты, указанную в roadmap.

## Продуктовый сценарий

Житель описывает проблему в боте → обращение сохраняется на сервере → оператор видит его на сайте → уточняет район и категорию → назначает ответственного → связывает проблему с городской мерой → рассматривает сценарий в симуляторе → сообщает жителю результат через бота.

Рабочее предположение: сайт — кабинет команды/оператора; жителю достаточно бота. Публичная страница при необходимости показывает только обезличенную статистику. Реальных обращений в акимат и полномочий исполнять работы проект пока не подтверждает: демонстрационные статусы нельзя выдавать за официальное решение городской службы.

Сейчас реализованы симулятор, серверная валидация, AI-пояснение и A/B. В проверенной локальной версии нет API жалоб, базы обращений и авторизации. Наличие карты в параллельной работе и её готовность нужно проверить при интеграции.

## Этап 1. Замкнуть путь обращения — P0

### TG-01. Приём жалобы в боте — Данияр

- Собрать текст, район или адрес; предложить геолокацию и фото как необязательные поля. Дать подтвердить обращение до отправки.
- Передавать обращение серверу через согласованный API. При временной ошибке сохранять запрос для повторной отправки.
- Показывать «Зарегистрировано» и номер только после подтверждения сохранения сервером. До этого — «Ожидает отправки».
- Дать жителю просмотр собственных обращений и их статусов.
- Подготовить отправку сообщений об изменении статуса; токен Telegram остаётся только у сервиса бота.

Готово, когда жалоба из реального бота появляется на сайте с тем же номером, а повтор отправки не создаёт ещё одну запись.

### API-01. Контракт интеграции — Азамат + Данияр

Первым шагом зафиксировать пример запроса, ответа и ошибок в отдельном контракте. Предлагаемые маршруты ниже ещё не реализованы:

- `POST /api/integrations/telegram/complaints` — создать обращение; 201 при создании, 200 при повторе той же отправки с тем же содержимым.
- `GET /api/complaints` и `GET /api/complaints/:id` — список с пагинацией/фильтрами и карточка для авторизованного оператора.
- `PATCH /api/complaints/:id` — изменить категорию, район, ответственного или статус с проверкой версии записи.
- `GET /api/integrations/telegram/notifications` — бот забирает предназначенные ему уведомления; отдельное подтверждение доставки по ID события.
- Отдельный маршрут получения статуса для бота с проверкой принадлежности обращения отправителю.

Вход: `schemaVersion`, стабильный `submissionId`, `telegramUserId`, `chatId`, `text`, `districtId` или `null`, необязательные `address`, `location`, `attachments`, `submittedAt`. Один `submissionId` обозначает целую подтверждённую жалобу, включая несколько сообщений/фото, и не меняется при повторе запроса. Идентификаторы Telegram передавать строками; время — ISO UTC. Сервер сам назначает ID, время получения и начальный статус.

Выход: `complaintId`, `publicNumber`, `status`, `createdAt`. Общие ошибки: `{code, message, retryable}`; 400/422 — исправить данные, 401/403 — доступ, 409 — конфликт, 429/5xx — повторить с задержкой. Повтор ключа с другим содержимым возвращает 409.

Готово, когда бот и сайт работают с одной согласованной схемой, известны серверный URL и способ аутентификации, а тестовый запрос проходит без ручного переноса данных.

### BE-01. Постоянное хранение — Азамат

- Создать базу, миграции и сущности: обращения, история изменений, вложения, связанные меры/сценарии, очередь уведомлений.
- Хранить исходный текст отдельно от исправленной классификации и AI-резюме. Отсутствующий район оставлять неизвестным до уточнения.
- Защитить создание уникальным ключом `submissionId`; сохранять обращение и событие для уведомления согласованно.
- Хранить статус, ответственного, приоритет с причиной, время создания/изменения, публичный ответ и внутренние заметки раздельно.
- Файлы хранить вне JSON обращения; согласовать с Данияром загрузку, допустимые типы, размер и доступ. Ссылки с токеном бота не передавать браузеру.

Готово, когда после перезапуска сервера обращения и история остаются, а повторная доставка создаёт одну запись. До выпуска проверить восстановление из резервной копии.

### UI-01. Кабинет обращений — Алишер, интеграция общего UI — Азамат

- Экран «Обращения»: номер, краткое описание, район, категория, статус, дата и ответственный.
- Поиск по номеру/тексту; фильтры по району, категории, статусу и дате; пагинация.
- Карточка: полный текст, доступные вложения, история, назначение ответственного, внутренний комментарий и отдельное поле ответа жителю.
- Состояния загрузки, отсутствия обращений, ошибки сохранения и повторной попытки; обновление списка без потери текущих фильтров.
- Для MVP достаточно периодического обновления с отметкой времени последней синхронизации; WebSocket не блокирует запуск.

Готово, когда оператор без терминала находит обращение, открывает его, назначает исполнителя и меняет статус. Ошибка сервера не отображается как успешное сохранение.

### FLOW-01. Статусы и обратная связь — Азамат + Данияр

Основной путь: «Новое» → «На рассмотрении» → «В работе» → «Решено». Дополнительно: «Нужно уточнение» с возвратом на рассмотрение, «Отклонено» с причиной, «Дубликат» со ссылкой на исходное обращение. Уточнение от жителя прикрепляется к прежнему обращению.

- Сервер проверяет переходы и роль пользователя. Закрытие требует пояснения; «Решено» требует описания результата. Повторное открытие фиксируется в истории.
- Оператор явно выбирает публичный ответ; внутренние заметки в Telegram не уходят.
- Изменение статуса и запись уведомления сохраняются одной транзакцией. Уведомления отправляются в порядке событий для одного обращения.
- Данияр обрабатывает доставку и сообщает результат серверу. Временные ошибки повторяются; блокировка бота отмечается как недоставка, не отменяя сохранённый статус.
- Стремиться подавлять повторы по ID события; учитывать, что при сбое после отправки до подтверждения возможна повторная доставка сообщения.

Готово, когда изменение на сайте приходит нужному жителю, а неудача доставки видна оператору и допускает повтор.

### OPS-01. Доступ и рабочее развёртывание — Азамат

- Вход для оператора/администратора; серверная проверка прав на каждое чтение и изменение. Регистрация жителей на сайте для MVP не нужна.
- Отдельная серверная аутентификация бота, ограничение частоты и размера запросов. Не отдавать Telegram ID, контакты и полный текст жалоб в публичные данные.
- Выводить пользовательский текст безопасно; вложения открывать только через проверку доступа. Согласовать сроки хранения и удаление персональных данных.
- HTTPS, постоянная база и файловое хранилище, секреты в конфигурации окружения, проверка здоровья приложения и базы, логи ошибок без текстов жалоб и токенов.
- Резервная копия, инструкция запуска, ответственный за сбои; лимиты AI-вызовов.

Готово, когда два сервиса доступны по рабочим адресам, посторонний не получает обращения, а перезапуск не теряет данные. Это часть P0 перед доступом реальных жителей.

## Этап 2. Связать обращения с ценностью симулятора — P1

### AI-01. Разбор жалобы — Азамат

Предлагать категорию, краткое резюме, район и возможные похожие обращения. Оператор может исправить результат. При неопределённости запрашивать уточнение; не назначать выдуманные координаты. Передавать модели только необходимый обезличенный текст, считать его данными, а не инструкцией. При недоступности AI сохранять жалобу и давать ручную обработку. Не закрывать и не объединять обращения автоматически.

Приёмка: неоднозначная жалоба не получает уверенный выдуманный район; отказ AI не мешает её регистрации.

### MAP-01. Проблемы по районам — Алишер + владелец карты

Показать на карте обращения с подтверждённым местом, остальные — в списке/сводке района. Фильтры карты и списка согласованы. Публичная карта использует агрегацию без точных адресов жителей. Отдельно считать обращения и уникальные проблемы: несколько жителей могут сообщить об одном случае.

Приёмка: выбор района показывает соответствующие обращения; отсутствие координат не скрывает жалобу и не создаёт случайную точку.

### SIM-01. Из проблемы в меру — Азамат + Алишер

- В карточке проблемы предложить подходящие меры из существующего каталога, а оператор подтверждает связь и район.
- «Добавить в сценарий» формирует черновик; действующие ограничения бюджета и пяти мер проверяются прежним ядром.
- Сохранять сценарий в базе с выбранными мерами, версией датасета и связанными обращениями; загружать после перезагрузки. A/B использует проверенные расчёты.
- Показывать отдельно прогноз симулятора, число связанных обращений и фактическое состояние работ.
- Количество жалоб не подставлять в формулу Score и не менять официальный датасет. Предлагаемая мера не означает, что проблема решена. Если подходящей меры нет, явно сообщить об этом.

Приёмка: жалоба → мера → валидный сценарий → расчёт → сравнение; регистрация новых жалоб не меняет контрольные числа симулятора.

### DASH-01. Сводка для команды — Алишер

Количество новых и открытых обращений, распределение по районам/категориям, число уникальных проблем, возраст открытых обращений и время до решения. Указывать период и правила расчёта. Не считать число жалоб объективной оценкой качества района: активность жителей различается.

Приёмка: карточки сводки ведут к соответствующей выборке; значения сходятся с базой при одинаковых фильтрах.

## Порядок выполнения

1. Азамат и Данияр фиксируют API-01, поля и статусы. Данияр делает сценарий бота; Азамат — BE-01 и интеграционные маршруты; Алишер — UI-01 на согласованных тестовых данных.
2. Интегрировать один минимальный путь: текстовая жалоба → база → список → карточка → смена статуса → сообщение в Telegram.
3. Закрыть OPS-01, вложения и восстановление после сбоев. Провести сквозную приёмку перед реальными пользователями.
4. Добавить AI-01, MAP-01, SIM-01 и DASH-01. Проверить общий пользовательский путь и регрессию симулятора.

При нехватке времени сокращать P1; сохранять надёжную регистрацию, кабинет, доступ и обратную связь. Голосовые жалобы, сложный автоматический поиск дубликатов, отдельный кабинет жителя и интеграции с городскими службами — следующий этап.

## Сквозная приёмка

- Реальная жалоба из бота появляется в кабинете, номер совпадает; повтор запроса и двойное нажатие не создают дубль.
- Обращение без фото/геолокации принимается; неподдерживаемое вложение отклоняется понятным сообщением.
- Недоступность API оставляет жалобу в очереди бота; после восстановления она доходит один раз на уровне записи в базе.
- Перезапуск сервера сохраняет данные и очередь уведомлений; восстановление резервной копии проверено.
- Статус и публичный ответ доходят нужному жителю; внутренний комментарий не отправляется; заблокированный бот отражается как недоставка.
- Неавторизованный запрос не читает жалобы; один житель через бота не получает чужое обращение; пользовательский HTML не исполняется.
- Одновременное редактирование не затирает изменения молча; оператор видит конфликт и обновляет карточку.
- Отказ AI не блокирует приём; прогноз симулятора не закрывает жалобу автоматически; прежние контрольные сценарии проходят.

Полная работа этапа подтверждена только после прохождения этой цепочки на развёрнутых сайте и боте. Наличие экранов и ответов API по отдельности недостаточно.
