# Контракт кабинетов и единого реестра обращений

Проект согласования, 23.09.2026. Это описание требуемого адаптера, а не сообщение о готовой публикации. Сопоставлены PR #21 (`1dc1858`) и hosted-реализация Данияра (`e93a930`, изменения `719b232`/`1ac60fa`, PR #25). Выбор PR #25/#28 и выпуск ведёт Азамат; после выбора сверить контракт с точным release SHA. В текущий UI-кандидат код PR #25/#28 не включён: сервер использует HTTP/complaints из `origin/main 898b9c8`. Hosted-контракт ниже описывает предложение для последующей интеграции владельцем реестра.

## Граница хранения

Единственный источник настоящих обращений — существующий `Complaints` Durable Object, экземпляр `city`, записи `complaint:<C-ID>`. Сохраняются его ID, tracking tokens, Telegram-квитанции, история, фото и миграция `v2-complaints`; существующий `AIBudget`/`v1` также сохраняется.

SQLite `src/desk/` из PR #21 содержит отдельные **демонстрационные** записи. Сейчас эти кабинеты работают на Node, а Worker их маршрутов не обслуживает. Их нельзя копировать в реальный реестр или выдавать за обращения жителей. Второй Durable Object/вторая копия реальных обращений не предлагаются. Простая загрузка HTML не делает кабинеты рабочими.

## Соответствие данных

- **ID:** desk — положительное число; реестр — `C-` и 16 hex-символов. Предпочтительно научить кабинеты принимать исходный строковый ID. Если временно нужны старые числовые ссылки, хранить только неизменяемое соответствие ID внутри того же `Complaints`, без копии обращения. Старые локальные demo-ID не сопоставлять автоматически с настоящими.
- **Текст, адрес, даты:** `text`, `address`, `createdAt`, `updatedAt` соответствуют напрямую. `districtId` использует `esil/almaty/saryarka/baikonur/nura`; desk `null` нормализуется в реестровое `''`. Координаты `location` и исходный `source:web|telegram` сохраняются; desk сейчас создаёт только `source:demo`.
- **Категория:** desk `transport/ecology/social/safety/services/other`; реестр `analysis.category:roads/utilities/waste/lighting/safety/other`. Автоматического взаимно-однозначного перевода нет. Кабинет должен показывать и редактировать реестровые категории; исходную категорию нельзя заменять приблизительным соответствием.
- **Приоритет:** desk `normal/high`; реестр `analysis.priority:low/normal/high`. Добавить `low` в кабинет; не повышать его до `normal` при сохранении несвязанного поля. Сохранять `analysis.summary/reason/duplicateOf/reviewed` и явно обозначать анализ правилами.
- **Ответственный:** desk требует `users.login`, реестр допускает строку `assignee` до 120 символов. Существующие назначения сохраняются, даже если ещё нет соответствующего аккаунта; новое назначение проверяется по согласованному списку сотрудников.
- **Версия:** desk использует integer `version`; реестр принимает `expectedUpdatedAt`. Кабинет должен посылать полученную серверную ревизию; адаптер перечитывает запись после чтения тела и до изменения, возвращает 409 при конфликте. Любые дополнительные данные кабинета требуют своей ревизии и общей атомарной операции, а не независимой записи после PATCH.
- **История и ответы:** desk разделяет внутренние `history/note` и публичные `replies/publicReply`; реестр хранит публичные `resolution` и историю статуса/назначения/решения. Внутренние комментарии не подставляются в `resolution` или публичную историю. Архив demo-ответов с `delivery:not_connected` не рассылается настоящим жителям.
- **Фото:** desk — BLOB и числовой ID; реестр — Telegram `fileId/fileUniqueId` и индекс вложения в безопасном представлении. Сохранять исходные ссылки на Telegram и проверять доступ через серверный фото-маршрут. Загрузка staff/resident-фото требует отдельного согласованного расширения вложений в том же реестре; текущий web-контракт фото не принимает.

## Статусы и полномочия

`new`, `resolved`, `rejected` совпадают. Desk `review`, `clarification`, `work` относятся к реестровому `in_progress`, но обратное преобразование неоднозначно. Рекомендуется сохранять реестровый статус без изменений, а детализацию рабочего этапа добавлять как отдельные метаданные кабинета. Для существующего `in_progress` показывать «В работе» без выдуманной истории этапов. Повторное открытие `resolved/rejected` проходит через `in_progress`; закрытие требует публичного решения.

Desk: cookie `desk_session` (8 часов, HttpOnly, SameSite=Strict), роли `admin/akim/operator`, защита `X-Desk-Request`. Реестр: `X-Admin-Token` для панели; webhook — отдельный Telegram secret. Сессии/роли кабинета должны проверяться внутри того же сервиса и давать доступ к общей операции реестра. Не пересылать публичному клиенту серверный admin token и не заменять им права ролей. Для HTTPS cookie обязателен Secure. Автоматического создания аккаунта/общего пароля нет: нужен согласованный закрытый provisioning.

Старый citizen tracking использует пару `{id, trackingToken}` и возвращает ограниченный публичный ответ. Resident из PR #21 использует отдельный ротируемый, хешированный bearer token, отзыв и фотографии. Старые tracking tokens нельзя отзывать или расширять их права при добавлении resident-функций. Персональные данные и внутренние заметки остаются закрытыми.

## Функции без готового эквивалента

Поручения и их приёмка; подтверждённые группы обращений; подписки/настройки сотрудника; недельные отчёты; сохранённые серверные сценарии; внутренние заметки; публичные результаты с выбранными фото «до/после»; отзыв жителя и повторное рассмотрение. Они требуют метаданных/связей по исходному C-ID в том же `Complaints`, правил ролей и атомарных переходов. `analysis.duplicateOf` — предположение правил, не эквивалент подтверждённой группы. Выполненное поручение не должно автоматически означать закрытое обращение.

## Рекомендуемая реализация и приёмка

1. Зафиксировать выбранный Азаматом release SHA. Сохранить существующие citizen/mayor/webhook маршруты и модель `store-core`. Добавлять адаптер кабинетов поверх общего сервиса; не импортировать Node `DatabaseSync` в Worker.
2. Сначала подключить защищённое чтение/фильтры/карточку и смену статуса к тому же обращению. Старый и новый кабинет должны видеть изменения друг друга; обновления из Telegram также видны обоим. Общая операция использует существующую валидацию и уведомления. Не обходить её прямой записью из нового UI.
3. Добавить согласованные метаданные по C-ID и ролевые сессии в тот же объект. Изменение обращения, метаданных и записи о необходимом уведомлении должно фиксироваться атомарно; фактическая доставка выполняется после фиксации. Текущий PATCH отправляет уведомление после изменения; гарантированная очередь требует отдельной реализации и не объявляется уже готовой.
4. Реализовать расширенные функции с проверками конфликтов, повторной отправки, прав, приватности фото, отзыва токенов и скрытия публикаций после повторного открытия. Demo-создание нельзя незаметно направить в боевой приём. До согласованного режима оно остаётся локальной демонстрацией.
5. Перед переключением Telegram перенести настоящие локальные записи по `docs/azamat-telegram-handoff.md`, без регенерации ID/токенов. Проверить старую квитанцию, историю и фото. Затем согласовать остановку polling; никакая правка UI сама по себе не переключает webhook.

Готовность означает рабочие `/desk.html`, все пять вкладок `/akim.html`, `/resident.html`, `/results.html`, а также прежние `/citizens.html` и `/mayor.html` в одном Worker, а не только HTTP 200 у HTML. Нужны проход полного пути одного обращения, сохранение после перезапуска, 409 при конкурирующих правках и неизменность контрольного расчёта симулятора. До выполнения этих проверок единый кабинет на production не заявляется готовым.
