# Проверяемые альтернативы одного решения

`buildPolicyOptions(scenario, { limit = 6 } = {})` из `src/core/policy-options.js` синхронно возвращает JSON-совместимый результат. Модуль импортирует только официальные `simulate` и `getDataset`; он не вызывает API, LLM, сеть или файловую систему, не добавляет зависимости и не меняет данные, формулу, пять решений или бюджет 100.

```js
import { buildPolicyOptions } from './src/core/policy-options.js';

const alternatives = buildPolicyOptions({ decisions: [
  { measureId: 'M7', districtId: 'nura' },
  { measureId: 'M8', districtId: 'nura' },
  { measureId: 'M10', districtId: 'nura' },
  { measureId: 'M12' },
  { measureId: 'M5', districtId: 'saryarka' },
] });
```

## Граница поиска

Одна замена сохраняет ровно четыре исходных решения. Пятое заменяется любой мерой каталога с любым допустимым для её типа районом. Можно сохранить меру и изменить только район. Городская мера не получает `districtId`. Сценарий с той же мерой дважды и неизменённый исходный сценарий исключаются до симуляции: они заведомо не являются допустимой альтернативой. Все остальные уникальные варианты проверяются через `simulate`, включая бюджет, направления и несовместимости.

Это **полный перебор внутри окрестности одного решения**, а не поиск глобального оптимума. Он не перебирает замены двух–пяти решений, не моделирует неизвестные эффекты и не превращает синтетический набор в прогноз для настоящего города.

На официальном наборе имеется 54 пары «мера / применимый район»: 10 районных мер × 5 районов и 4 городские. Поиск ограничен пятью заменяемыми решениями; максимум 270 попыток до исключения повторов. Он не перебирает все сочетания пяти мер. Вход не изменяется, результаты не кэшируются, каждый вызов полностью воспроизводим. В валидных сценариях решения канонически сортируются по номеру меры; идентификаторы, числовое накопление официального симулятора и порядок ответа не зависят от порядка входных решений.

## Контракт ответа

| Поле | Значение |
| --- | --- |
| `valid` | Прошёл ли исходный сценарий официальную проверку. Это не признак наличия альтернатив. |
| `scope` | Всегда `'single-decision-neighborhood'`. |
| `exhaustiveWithinScope` | `true` после полного перебора валидного исходного сценария, даже при ограниченном выводе. `false` для невалидного входа, когда поиск не запускался. |
| `baseline.scenario` | Независимый канонический снимок исходного валидного сценария. Для ошибочного входа сохраняется его снимок; отсутствующий вход представлен `null`. |
| `baseline.result` | Полный результат `simulate` исходного сценария без пересчёта или округления. |
| `explored` | Число уникальных замен с пятью разными мерами, переданных в `simulate`; исходный сценарий не считается. Включает невалидные по другим правилам замены. |
| `validCandidates` | Сколько из `explored` прошло все правила симулятора. |
| `paretoCandidates` | Число недоминируемых полезных альтернатив до ограничения вывода. |
| `limit` | Нормализованный предел вывода: конечное число округляется вниз и ограничивается диапазоном 0–12; иные значения, включая строки, `null`, `NaN` и бесконечность, дают 6. |
| `truncated` | `paretoCandidates > options.length`. |
| `options` | От нуля до `limit` альтернатив по схеме ниже. |
| `errors` | Официальные ошибки исходного сценария; для валидного входа `[]`. |
| `emptyReason` | `null` либо `{ code, message }` с объяснением пустого ответа. |

Одна альтернатива:

```js
{
  id: 'single:M3:nura|M7:nura|M8:nura|M10:nura|M12:*',
  scenario: { decisions: [/* пять канонических решений */] },
  result: {/* полный неизменённый результат simulate(scenario) */},
  delta: {
    score: 0.66249,            // пример округлён только в документации
    worstDistrictScore: 2.02,
    totalCost: 5,              // положительное число означает больший расход
    criticalCount: 0
  },
  changed: {
    removed: { measureId: 'M5', districtId: 'saryarka' },
    added: { measureId: 'M3', districtId: 'nura' }
  },
  objectives: {
    maximizeScore: 'improved',
    maximizeWorst: 'improved',
    minimizeCost: 'worse'
  },
  selectedFor: ['maximizeScore', 'maximizeWorst']
}
```

Все `delta` равны **результат альтернативы минус исходный результат**. `deltaScore` внутри `result`, напротив, сохраняет смысл официального симулятора: прирост к городу без мер. Интерфейс берёт цифры из `result` и `delta`, не реализует формулу повторно. `changed` содержит идентификаторы; названия берутся из датасета. `id` описывает канонический конечный сценарий, не его позицию в списке, и пригоден как ключ интерфейса, но не служит подтверждением подлинности клиентского результата.

## Парето, приоритеты и честные компромиссы

Альтернатива доминирует другую, если её Score и оценка худшего района не меньше, стоимость не больше и хотя бы одно из этих неравенств строгое. Сравнение идёт по полным неокруглённым числам официального симулятора. Число критических показателей показано отдельно и **не является четвёртой целью Парето**; его влияние уже входит в официальный Score.

Каждый возвращённый вариант:

1. Не доминируется ни одним валидным кандидатом или исходным сценарием.
2. Улучшает хотя бы одну из трёх целей относительно исходного сценария.
3. Может ухудшать остальные цели; это явно отражают дельты и `objectives`.

Для каждой цели статус — `'improved'`, `'unchanged'` или `'worse'`. Для стоимости улучшение означает отрицательную `delta.totalCost`; для двух оценок — положительную дельту. Равные исходному сценарию по всем трём целям варианты не выдаются. Равные друг другу по метрикам полезные варианты могут оставаться разными проверяемыми сценариями.

Сначала выбираются лидеры фронта Парето по Score, худшему району и минимальной стоимости, в таком порядке и без повторов. Каждый получает в `selectedFor` все цели, по которым выбран лидером. Остальные кандидаты получают `['tradeoff']` и идут по убыванию Score. Равенство разрешается оценкой худшего района, затем меньшей стоимостью, затем лексикографическим `id`. Для приоритета худшего района и стоимости сначала сравнивается соответствующая цель, затем тот же порядок Score / худший район / стоимость / `id`.

`selectedFor` описывает приоритет **среди найденного фронта**, не обещание улучшить исходный сценарий по этой цели. При `limit < 3` все три различных лидера могут не поместиться. Ограничение вывода не сокращает сам перебор; `limit: 0` не подходит для экономии вычислений.

Коды пустого состояния:

| `emptyReason.code` | Смысл |
| --- | --- |
| `INVALID_BASELINE` | Официальная проверка отклонила вход; `options: []`, все счётчики 0, ошибок достаточно для исправления выбора. |
| `NO_VALID_ALTERNATIVES` | Все перечисленные замены невалидны. |
| `NO_IMPROVING_ALTERNATIVES` | Нет недоминируемой замены с улучшением хотя бы одной цели. Это также объясняет случай, когда исходный сценарий доминирует все замены. Глобальная оптимальность не утверждается. |
| `LIMIT_ZERO` | Фронт существует, но вызывающая сторона запросила ноль выводимых вариантов. |

## Проверенный пример

Официальный A имеет стоимость **95**, Score **56.54307** и худшую районную оценку **52.96250**. Для него проверена 181 уникальная замена; 117 валидны, 5 входят в выдаваемый фронт:

| Вместо M5 / Сарыарка | Стоимость | Score | Худший районный балл |
| --- | ---: | ---: | ---: |
| M3 / Нура | 100 | 57.20556 | 54.98250 |
| M11 / Нура | 80 | 56.69056 | 53.73250 |
| M14 / город | 86 | 56.98582 | 53.57500 |
| M5 / Нура | 95 | 56.87287 | 54.17500 |
| M1 / Нура | 88 | 56.83682 | 54.08750 |

Порядок таблицы совпадает с выдачей: лидер Score/худшего района, лидер экономии, остальные компромиссы. Числа таблицы округлены до пяти знаков; JSON сохраняет исходную точность. У всех пяти `criticalCount = 0`. Это сравнение относится к синтетическим данным и горизонту официальной модели.

## Проверки и время расчёта

Проверено 23.09.2026 на базе `6fcc4c`, Node.js **24.19.0**, Windows x64, AMD Ryzen 5 7535HS. Команда:

```powershell
node --test tests/policy-options.test.js tests/simulator.acceptance.test.js
```

Результат: **35 passed, 0 failed**, около 1.12 с. Десять новых проверок охватывают точный A и замену M3, сохранение результата/дельт, независимый полный перебор A/B/C и проверку доминирования, смену только района, явный компромисс цены и Score, отказ при стоимости 105, ошибочные поля, все 120 перестановок, неизменность входа/датасета/следующих ответов и границы `limit`. Остальные 25 — существующая официальная приёмка симулятора. Независимый перебор тестов использует официальный симулятор как источник чисел, но не импортирует алгоритм генерации, сортировки или сравнения модуля.

Отдельный замер без кэша: первый вызов A в новом процессе — **16.06 мс wall time**, `process.cpuUsage()` — **16 мс CPU**. Далее по 100 вызовов каждого из существующих сценариев A/B/C из `docs/scenario-comparison.md`:

| Сценарий | p50 wall, мс | p95 wall, мс | max wall, мс | CPU всей серии, мс | Среднее CPU на вызов, мс |
| --- | ---: | ---: | ---: | ---: | ---: |
| A, 117 валидных | 6.03 | 8.84 | 10.30 | 938 | 9.38 |
| B, 177 валидных | 8.17 | 13.05 | 16.31 | 921 | 9.21 |
| C, 105 валидных | 5.20 | 7.80 | 8.86 | 610 | 6.10 |

Wall time измерялся `performance.now()`, CPU — разностью `process.cpuUsage()` до/после всей серии. CPU одиночного вызова на Windows грубо дискретен: наблюдались 0/15/16 мс, поэтому ноль не означает отсутствие работы. Среднее CPU серии не является верхней границей отдельного запроса. Node CPU учитывает процесс, включая сопутствующую работу V8; это не измерение Cloudflare.

Профиль встроенным `node:inspector/promises` за отдельные 200 вызовов A получил 865 выборок: `structuredClone` — 204, `simulate` — 130, `buildPolicyOptions` — 44, `addEffects` — 41, сборка мусора — 35, `validateScenario` — 29, анонимные функции — 324. Большая часть именованных выборок связана с официальным симулятором и его копированием данных. Его формула и реализация ради этого модуля не менялись.

**Лимит Worker 10 мс CPU не подтверждён и для холодного полного перебора небезопасен.** Этот PR не подключает модуль к публичному маршруту. Кэш по каноническому сценарию сократил бы только повторные обращения и не решил бы холодный запрос; в модуле кэша нет. После отдельного измерения интегратор может выбрать вычисление в браузерном Worker либо заранее рассчитанный демонстрационный результат; применение выбранного сценария должно снова проходить серверный `simulate`.

У самого модуля нет Node-специфичных зависимостей. Однако в базе `6fcc4c` импортируемый `simulator.js` читает JSON через `node:fs`: переносимость всей цепочки в браузер/Worker зависит от отдельной согласованной адаптации симулятора. В этом изменении она не выполнена и работа в Cloudflare не заявляется.
