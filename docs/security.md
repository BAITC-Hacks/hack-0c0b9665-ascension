# Безопасность и модель угроз

Общий реестр команды имеет отдельные роли, короткие подписанные сессии, отзыв cookie, журнал публикаций и атомарную проверку ревизий. Его конфигурация обязательна: без неё HTTP-маршруты возвращают 503 до доступа к хранилищу. Контракт доступа и ограничения изложены в [workspace.md](workspace.md), доверенные транспортные данные и защита файловой базы — в [workspace-runtime.md](workspace-runtime.md).

API симулятора публичен и работает с синтетическими данными; для него нет регистрации, авторизации и серверного хранилища личных сценариев. Отдельный модуль обращений граждан работает в Node и Worker, имеет собственный доступ администратора и хранит пользовательские сведения; его границы описаны ниже. Доступность вычислений, целостность формулы, конфиденциальность ключей и обращений, а также ограничение платных запросов — основные защищаемые свойства. Этот документ описывает реализованные меры и их пределы; он не является результатом внешнего аудита или сертификацией.

## Границы доверия

Недоверенными считаются HTTP-запросы, импортируемые файлы, браузерное хранилище, названия из географического поиска, Telegram updates и ответы AI-провайдера. Сервер доверяет поставляемому набору `data/city.json` и своему коду. Браузер получает публичные данные и результат расчёта, но не ключ AI или бота. AI-провайдер получает синтетические факты выбранного сценария; обращения классифицируются локальными правилами и в AI-пояснение не передаются. Клиент не задаёт произвольный URL серверного запроса; Telegram transport использует адреса API Telegram.

Посетитель может послать собственный HTTP-запрос без интерфейса, изменить JSON, заголовки и localStorage, отправить много параллельных запросов или попытаться вызвать API с другого сайта. Защита не предполагает честность такого клиента. Контроль инфраструктурного аккаунта, сборочного окружения и локальной файловой системы находится за пределами HTTP-модели угроз.

## Угрозы, меры и проверка

| Угроза | Реализованная мера | Проверка / граница гарантии |
| --- | --- | --- |
| Подмена цены, бюджета, Score или набора данных | Строгая валидация сценария и новый расчёт в общем API перед объяснением | Приёмочные тесты ядра, HTTP-тесты клиентских overrides, тесты фактов AI |
| Слишком большой или неверный запрос | 32 KiB по байтам потока, JSON media type, отказ от сжатого тела, фиксированные методы/маршруты | Тесты неверного JSON, media type, заявленного и потокового превышения размера |
| Чтение `.env` и исходников через статику | Проверка пути; в Node — проверка разрешённого корня и реального пути, включая symlink; Cloudflare Assets настроен на `public` | HTTP-тесты traversal, приватных файлов и MIME; содержимое `public` должно оставаться публичным |
| Утечка ключа или внутренних деталей в ошибке | Ключ только в серверном окружении; ошибки API сериализуются без stack/path; клиент видит только boolean готовности | Тесты приватности ключа, исключений и fallback; `aiConfigured` не подтверждает работоспособность провайдера |
| XSS через текст модели, импорт и поиск | Текст выводится через `textContent` либо escaping; импорт сохраняет проверенные решения и отбрасывает чужие Score/AI-текст; CSP ограничивает источники | Тесты импорта, review мест вставки DOM и браузерная проверка; CSP не заменяет escaping |
| Запросы из чужой браузерной страницы | POST симулятора проверяет точный `Origin` и `Sec-Fetch-Site`; обращения используют отдельную проверку host; webhook проверяет секрет | JSON и отсутствие разрешающего CORS дополнительно ограничивают браузер; запросы без browser headers разрешены для CLI, поэтому Origin не является аутентификацией |
| Расходование бюджета через AI API | Ограничения попыток, частоты и одновременности; для Cloudflare — обязательный постоянный бюджет до вызова провайдера | Тесты конкурентного допуска, отсутствующего/ошибающегося хранилища и перезапуска SQLite |
| Ошибка или зависание AI | Timeout, проверка структуры и размеров текстовых полей, детерминированное пояснение с честным режимом; слот освобождается в `finally` | Mocked transport/timeout/refusal/error tests; числа остаются результатом симулятора |
| Изменение политики только на одном хостинге | Общий `SECURITY_HEADERS` и автоматическая сверка с `public/_headers` | `node scripts/check-quality.js`; заголовки живого развёртывания проверяются отдельно |

## Платные обращения и доступность

Локальный Node guard хранит состояние в одном процессе. По умолчанию разрешены 100 попыток, 10 в минуту и 2 одновременно; конфигурация ограничивается допустимыми диапазонами. Перезапуск процесса сбрасывает эти счётчики, несколько процессов не разделяют их. Поэтому локальный лимит нельзя считать глобальным финансовым ограничением.

В Cloudflare все экземпляры обращаются к одному Durable Object `global`. `AIBudgetState.acquire()` атомарно проверяет и записывает допуск в SQLite: 100 попыток за время существования хранилища, 10 в минуту, 2 одновременно. Ошибка провайдера также расходует попытку. `release()` освобождает только одновременность; прерванное обращение занимает слот до истечения 65-секундной аренды. Проверка и запись выполняются в синхронной транзакции, до сетевого вызова. Семантика транзакций описана в [документации Cloudflare SQLite storage](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/).

Платформенный rate limiter и локальный guard — дополнительные барьеры. Ошибка обязательного rate limiter или постоянного бюджета запрещает платный вызов и оставляет расчётное пояснение. Локальный guard перепроверяет доступность после асинхронного обращения к платформе; конкурентные запросы не должны использовать устаревшее разрешение. Ошибка освобождения lease не вызывает повторный запрос к провайдеру.

100 попыток — лимит количества, а не суммы денег: стоимость зависит от модели и токенов. Анонимный пользователь способен израсходовать доступные попытки, после чего остальным останется детерминированное пояснение. Эти ограничения также не обеспечивают полную защиту вычислительного API от DoS. Для постоянного публичного сервиса нужны эксплуатационные лимиты, мониторинг и отдельное решение о доступе к платной функции.

## Браузер и внешние сервисы

Для API симулятора в Node за TLS reverse proxy задаётся доверенный публичный origin: параметр `publicOrigin` при создании сервера, затем `PUBLIC_ORIGIN` из окружения, затем автоматически предоставляемый Render `RENDER_EXTERNAL_URL` (в этом порядке). Например, `PUBLIC_ORIGIN=https://city.example`. Разрешены только HTTP(S) адреса без пути, credentials, query и fragment; ошибочная конфигурация останавливает запуск. Render публикует свой адрес в [документированной переменной окружения](https://render.com/docs/environment-variables#render_external_url), поэтому стандартный Blueprint не требует изменения. Для custom domain следует задать `PUBLIC_ORIGIN` явно. Без этих настроек используется origin прямого соединения. Заголовки `Forwarded` и `X-Forwarded-*` не считаются доверенной конфигурацией. Регрессионные HTTP-тесты проверяют HTTPS origin поверх внутреннего HTTP, отказ чужому origin и поддельным proxy headers. Это проверка origin браузера, а не идентификация клиента.

CSP разрешает собственные скрипты, выбранные origins карты/поиска, `blob:` workers для карты и inline styles, необходимые текущему интерфейсу. `object-src 'none'` и `frame-ancestors 'none'` запрещают плагины и встраивание страницы; дополнительные заголовки включают `nosniff`, `no-referrer` и запрет камеры и микрофона. Геолокация разрешена только своему origin (`geolocation=(self)`) для формы гражданина и всё равно требует разрешения пользователя в браузере. Разрешённые `style-src 'unsafe-inline'` и `worker-src blob:` являются явными компромиссами текущей карты, а не строгой политикой без исключений. Назначение CSP описано в [MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP).

Cloudflare `_headers` относится к статическим ответам; динамический Worker устанавливает заголовки сам. Поэтому оба пути проверяются отдельно и сверяются в CI, согласно [документации Static Assets headers](https://developers.cloudflare.com/workers/static-assets/headers/).

Карта и поиск обращаются к внешним сервисам непосредственно из браузера. Их операторы могут видеть сетевой адрес и запрос; работа карты зависит от доступности этих сервисов. Локальная библиотека сценариев доступна скриптам того же origin и пользователю устройства, не синхронизируется между устройствами и не предназначена для секретных или персональных данных. Повреждённое хранилище не очищается молча, ошибки записи не выдаются за успех.

## Проверки и эксплуатационные ограничения

`npm test` выполняет проверки ядра, HTTP, AI fallback, квот, импорта, обращений и Telegram с подставным транспортом, без реального платного обращения или доставки сообщения. CI проверяет Node.js 24 на Windows и Linux, использует `contents: read`, отключает сохранение Git credentials и закрепляет сторонние actions полными commit SHA. Запуск тестов не доказывает отсутствие всех уязвимостей; браузер, фактические заголовки, внешний runtime и опубликованная версия требуют отдельной проверки.

Секреты задаются через окружение или секретное хранилище платформы. Значения не должны попадать в `public`, Git, логи запросов, экспорт сценария или документацию. При компрометации ключ нужно отозвать у провайдера и заменить в окружении; удаление файла из текущего checkout само по себе не удаляет секрет из истории.

В модуле симулятора нет пользовательской идентификации, разграничения ролей, аудита действий пользователей или договорённостей об обработке персональных данных. Для реального муниципального применения также необходимы проверенные локальные данные и отдельная оценка модели. Текст AI остаётся недоверенным пояснением: проверка JSON-структуры не гарантирует фактическую правильность каждой формулировки.

## Отдельный модуль обращений граждан

Node и Worker подключают общие `src/complaints/route-core.js` и `store-core.js`; их API и представления описаны в [контракте обращений](citizen-contract.md). Они используют общий ограниченный JSON parser и защитные заголовки, сохраняя отдельные правила доступа и безопасные сообщения об ошибках хранилища. Worker направляет маршруты обращений и webhook в `COMPLAINTS.getByName('city')`. Отсутствующий или неисправный binding возвращает ошибку; временное непостоянное хранилище вместо него не создаётся.

**Доступ.** Список, изменение статуса и фото требуют `ADMIN_TOKEN`. Только локальный Node-режим без токена допускает администратора по одновременно loopback-соединению и localhost Host. Worker не включает это исключение даже под `wrangler dev`. Telegram webhook проверяет `TELEGRAM_WEBHOOK_SECRET` до чтения тела и отправки сообщений; отсутствие секрета или токена бота отключает обработку. Браузерная проверка Origin не применяется вместо webhook-секрета. Доступ по одному общему admin token не является системой отдельных учётных записей сотрудников.

**Разные правила Origin.** Обращения сравнивают host из HTTP(S) Origin с host запроса и отвергают `Sec-Fetch-Site: cross-site`; схема отдельно не сравнивается. Они не используют строгий `PUBLIC_ORIGIN` API симулятора. При размещении Node за публичным proxy обязателен `ADMIN_TOKEN`, proxy должен сохранять внешний Host. Fetch-адаптер Worker берёт host из URL запроса, не из присланного клиентом Host. Поэтому проверки симулятора и обращений остаются отдельными контрактами.

**Приватные поля.** Создание требует явного согласия. Публичная HTTP-форма не может задать Telegram identity или начальный статус. Запись содержит текст, адрес, координаты и при Telegram-приёме chat ID и метаданные фото; это могут быть персональные сведения. Проверка статуса требует номера и случайного личного кода, а внутри исходного Telegram-чата возможна проверка принадлежности чату. Публичное представление не возвращает исходный текст, адрес, координаты и фото; admin DTO исключает личный код проверки, chat ID и Telegram file ID. Сам код выдаётся владельцу в квитанции и хранится в базе, поэтому доступ к базе также даёт доступ к нему. Поля исполнителя, решения и история статусов доступны владельцу кода: сотрудник не должен помещать туда чужие приватные данные. Фото запрашиваются через защищённый серверный маршрут без раскрытия токена бота браузеру.

**Хранение.** Node хранит JSON вне `public`, сериализует записи в одном процессе и заменяет файл через rename; для него необходимы постоянный диск и единственный writer. Worker хранит записи обращений и Telegram-сессии в SQLite-backed Durable Object; изменение обращений выполняется транзакционно. Миграция `v2-complaints` добавляет `Complaints`, сохраняя `v1` и независимую квоту `AIBudget`. Общая логика обращений использует `node:crypto`/`Buffer`, доступные через [Node API compatibility Workers](https://developers.cloudflare.com/workers/runtime-apis/nodejs/); файловый адаптер в Worker не используется. Автоматического переноса локальных данных в облако, политики удаления обращений, ротации личных кодов и полной системы резервного восстановления здесь нет. Истечение TTL диалога не означает удаления самого обращения.

**Повторная доставка.** Облачный черновик действует 30 минут бездействия. Постоянный журнал `update_id` ограничивает повторную обработку окном 24 часа; сохранённые идентификаторы отправленного черновика и update дополнительно защищают создание обращения. Подготовленный ответ сохраняется до сетевой отправки, чтобы повтор запроса не повторял изменение черновика. Гарантии единственной доставки сообщения нет: если Telegram принял сообщение перед сетевым сбоем, повтор может доставить его ещё раз. После окончания окна журнал не обеспечивает бессрочную защиту от replay. Локальный незавершённый диалог не переносится при переключении в hosted-режим.

**Нагрузка и проверки.** Приём обращений и поиск статуса ограничены 30 запросами в минуту на адрес в памяти экземпляра; это не постоянная глобальная защита от DoS. Node использует адрес соединения, Worker — адрес из платформенного `CF-Connecting-IP`; proxy и перезапуски влияют на эти ограничения. Отдельные `complaints-worker.test.js`, `complaints-durable.test.js`, `telegram-persistence.test.js` и `telegram-mode.test.js` проверяют доступ, приватность, ошибки storage, восстановление сессий и переключение режима. Хранилище и транспорт в этих тестах подставные: проверка сборки и runtime Cloudflare остаётся отдельным этапом. Режимы и настройка секретов описаны в [Telegram hosting](telegram-hosting.md).
