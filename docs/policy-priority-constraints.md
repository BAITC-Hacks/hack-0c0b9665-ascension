# Приоритеты при поиске альтернатив

Проблема: лучший общий индекс мог предлагать убрать обязательную меру или ухудшить важный для руководителя показатель. Теперь поиск принимает точные закрепления решений и один защищённый показатель. Например, можно оставить перевод частного сектора на чистое топливо именно в Сарыарке и не допускать ухудшения качества воздуха относительно текущего рассчитанного плана.

## Контракт расчёта и транспорта

`buildPolicyOptions(scenario, {limit, constraints})` сохраняет прежнее поведение при отсутствии `constraints` или при пустых ограничениях. Исходный симулятор, данные и формула не изменяются.

```js
const constraints = {
  lockedDecisions: [{ measureId: 'M5', districtId: 'saryarka' }],
  protectedIndicator: { indicatorId: 'E2', districtId: 'saryarka' },
};
buildPolicyOptions(scenario, { limit: 6, constraints });
```

- `lockedDecisions` — максимум пять точных решений текущего сценария. Отсутствующий район допустим только для городской меры. Нельзя заменить закреплённую меру или перенести её в другой район. Дубликаты, неизвестные поля, незадействованные меры и другой район отклоняются.
- `protectedIndicator` — `null` либо известный `indicatorId` и необязательный известный `districtId`. Без района проверяются все пять районов по отдельности. Для каждого защищённого района значение `candidate.after[indicatorId]` должно быть не меньше `baseline.result.after[indicatorId]` этого района. База — результат текущего плана на горизонте модели, а не начальные городские значения.
- Неверный объект ограничений даёт `valid:false`, `INVALID_CONSTRAINTS`, `exhaustiveWithinScope:false`, нулевой перебор и пустые варианты. Поля нельзя молча отбрасывать в адаптере.
- Все пять решений закреплены: `valid:true`, `ALL_DECISIONS_LOCKED`, нулевой перебор, явное предложение снять закрепление.

Панель передаёт прежнее тело `{decisions}` без активных ограничений. При активных ограничениях тело имеет форму `{scenario:{decisions}, constraints}`. Владелец браузерной интеграции должен пропустить `constraints` через fetch-совместимый клиент и сообщение Worker `{requestId,scenario,limit:6,constraints}`, затем передать его в опции ядра. В этом изменении клиент, Worker entry и сгенерированный bundle **не меняются**; подключение выполняет их отдельный владелец после merge.

Ответ сохраняет `scope:'single-decision-neighborhood'` и добавляет:

| Поле | Значение |
|---|---|
| `constraints` | Независимая каноническая копия принятых ограничений; `null` при ошибке до их принятия |
| `constraintScope` | `unrestricted` или `constrained` для успешного расчёта |
| `explored` | Все уникальные замены незакреплённых решений, переданные официальному симулятору |
| `validCandidates` | Варианты, прошедшие и правила симулятора, и защиту показателя |
| `rejectedByConstraints` | Валидные по симулятору варианты, отвергнутые защитой показателя; закреплённые слоты вообще не перебираются |
| `options[].worsenedIndicators` | Все ухудшения относительно рассчитанной базы: `districtId`, `districtName`, `indicatorId`, `indicatorName`, `baseline`, `value`, `delta` |

Вначале полностью перебирается допустимое пространство одной замены и применяются ограничения. Затем рассчитываются варианты Парето по общему индексу, слабейшему району и стоимости, и только после этого ограничивается длина выдачи. Это не глобальная оптимизация и не полный фронт без ограничений. `exhaustiveWithinScope` означает полноту только в заданной области.

## Поведение панели

Ограничения находятся в закрытом по умолчанию `details`: пять флажков с названиями мер и районов, показатель и территория защиты. Краткое описание активных ограничений видно даже при закрытом блоке и повторяется с результатами. Каждая карточка содержит раскрываемый список ухудшений районных показателей с исходным и новым значением модели.

Изменение любого ограничения отменяет запрос и удаляет прежние варианты. Проверяется совпадение ограничений в ответе, сохранение закреплённых решений и фактическое отсутствие ухудшения защищённого показателя; ответ старого адаптера, проигнорировавшего ограничения, не показывается. Старые кнопки загрузки перестают работать. При смене города, изменении/загрузке сценария или новом расчёте ограничения сбрасываются вместе с прежним снимком. Другой город без данных модели не получает расчётных возможностей.

Выбранный вариант передаётся только через `scenario:load`; после загрузки пользователь заново запускает проверку сервером. Защита относится к синтетической модели и не гарантирует реального эффекта.

## Проверка 23.09.2026

Команда: `node --test tests/policy-options.test.js tests/policy-panel.test.js` — **42/42 PASS**. Независимый тестовый перебор сначала отбирает все допустимые варианты по закреплениям/защите и лишь затем ищет фронт: совпали состав, количество и ограничение выдачи. Проверены отсутствие переноса закрепления, общегородская и районная защита, неверные поля, все пять закреплений, детерминизм и отсутствие изменения входа. Панель проверена на отмену запросов, устаревшие и ложные ответы, сброс, отсутствие данных и читаемые ухудшения.

Браузер: локальный изолированный HTTP-стенд с настоящим модулем панели и настоящим `buildPolicyOptions`, без AI и без браузерного Worker. У официального примера закрепление M5/Сарыарка и защита E2/Сарыарка дают 144 проверенные замены, 86 допустимых, 7 вариантов Парето и 6 показанных. Ухудшения раскрываются с названиями районов и показателей. При всех пяти закреплениях выведена точная причина отсутствия замен. При viewport 390 px измерены `document.scrollWidth=390`, ширина панели 374 px и `panel.scrollWidth=374`.

Ограничение доказательств: сквозной публичный маршрут через обновлённые клиент, Worker и bundle проверяет интегратор после подключения; локальный стенд не подменяет эту проверку.
