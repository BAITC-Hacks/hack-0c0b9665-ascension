# Общий реестр команды: отдельное подключение

Модуль добавляет к локальному реестру явные получение и публикацию общей версии. Доступ выключен, пока оператор не задаст конфигурацию. Этот PR предоставляет сервис, хранилища и панель; HTTP-маршруты, binding/migration Cloudflare и mount в приложении подключает интегратор отдельно. Наличие кода не означает, что общее хранение уже включено на публичном сайте.

Это рабочий прототип для небольшой команды, не официальная система поручений. Публикация не отправляет уведомления исполнителям и не подтверждает выполнение. Снимки модели, адреса, сметы и KPI остаются введённым человеком контекстом. Сервер проверяет структуру, доступ и версию; достоверность фактов он не удостоверяет.

## Доступ и конфигурация

Все три значения обязательны. Пустая или неверная конфигурация даёт `503 WORKSPACE_DISABLED` на всех маршрутах; анонимное чтение и запись запрещены.

| Значение | Контракт |
| --- | --- |
| `WORKSPACE_ORIGIN` | Точный внешний origin без завершающего `/`, например HTTPS-адрес приложения. Только HTTPS, кроме HTTP для `localhost`, `127.0.0.1` или `[::1]`. Не вычислять из Host/X-Forwarded-* входящего запроса. |
| `WORKSPACE_SESSION_SECRET` | Секрет оператора длиной 32–512 символов, с высокой случайной энтропией. Хранить только на сервере. Ротация завершает все сессии. |
| `WORKSPACE_ACCESS_POLICY` | Серверный JSON-массив 1–20 записей с точными полями `id`, `name`, `role`, `tokenHash`. Уникальные строковые ID и SHA-256 хеши; `tokenHash` — 64 строчные hex-цифры от ключа доступа. Роли: `owner`, `editor`, `viewer`. |

Ключи доступа — случайные секреты длиной 32–512 символов, выдаваемые оператором отдельно. Репозиторий не содержит рабочих ключей, не создаёт их автоматически и не рассылает приглашения. Хеширование не делает короткий пароль надёжным: использовать случайный ключ, а не человеческий пароль. Значения политики и секретов нельзя передавать в браузерный bundle или журналы.

`owner` и `editor` могут читать и публиковать весь реестр; `viewer` может читать реестр и журнал, но запись получает 403. Изменение ролей, выдача и отзыв ключей выполняются оператором через серверную политику, интерфейса управления пользователями нет. Если ключ выдан нескольким людям, журнал отмечает имя этого общего доступа — персональное авторство не доказано.

Сессия длится 15 минут. Cookie: `HttpOnly`, `SameSite=Strict`, `Path=/api/workspace`, `Secure` при HTTPS в **настроенном** origin, включая размещение Node за TLS-прокси. HMAC подписывает сессию; проверки подписи и отпечатка политики используют Web Crypto verification. Каждая операция заново сверяет текущую политику: удаление/изменение ключа или роли инвалидирует ранее выданную сессию. Выход отзывает её ID в хранилище и очищает cookie; повтор старой cookie не работает. Ключ не сохраняется панелью.

Перед чтением тела сервер проверяет конфигурацию, Origin/Sec-Fetch-Site, маршрут, метод и, кроме входа, сессию/роль. Изменяющие запросы требуют точного Origin. В URL нет параметров авторизации, любые query-параметры отклоняются. JSON читается потоком с лимитом **128 КиБ UTF-8**, независимо от Content-Length. Другие Content-Type и неверный JSON отклоняются.

## Контракт HTTP и хранилищ

`createWorkspaceHandler({ repository, getConfig, now? })` из `src/workspace/handler.js` возвращает `handleWorkspace(request, { clientAddress } = {}) → Promise<Response>`.

| Маршрут | Метод и результат |
| --- | --- |
| `/api/workspace/session` | GET → `{enabled:true,identity:{id,name,role},expiresAt}`; POST `{accessKey}` → та же сводка и cookie; DELETE → выход. |
| `/api/workspace/register` | GET → `{revision,document}`. Начальное состояние: ревизия 0 и пустой документ схемы 2. PUT `{expectedRevision,document}` → новая ревизия и документ. |
| `/api/workspace/audit` | GET → `{entries}`; последние 50 публикаций в обратном порядке. Доступно всем трём ролям. |

Ошибки: `{error:{code,message,...}}`. Основные статусы: 401 — нет сессии; 403 — роль/Origin; 409 — конфликт, `error.currentRevision`; 422 — схема; 413 — размер; 429 — ограничение входа с `Retry-After`; 503 — не настроено. Все ответы `Cache-Control: no-store`. Не преобразовывать Response повторным JSON-кодированием: сохранить статус, Set-Cookie и Retry-After, добавить общие security headers приложения. Для Node несколько cookie переносить через `headers.getSetCookie()`; HEAD не отправляет тело.

Документ: `{schemaVersion:2,registers:[...]}`, максимум 10 наборов по 5 поручений. Сервер импортирует **тот же чистый** `normalizeActionDocument` из `public/action-register.js`, что используется локальными hook. Лишние поля, неизвестная версия, неверные статусы, вложенные структуры и переполнение отклоняются целиком; схема не расходится между браузером и сервером. Импорт функции не обращается к DOM. Клиентская роль не является входом авторизации.

`createSqliteRepository(path)` из `src/workspace/node-sqlite.js` требует явного пути постоянной базы вне `public/`. Создать родительскую папку должен оператор/адаптер. Node 24, встроенный SQLite, WAL, busy timeout. Обработчик не открывает БД при импорте. `close()` завершает подключение.

`TeamWorkspaceDurableObject` из `src/workspace/cloudflare.js` использует SQLite-backed DO и `storage.transactionSync`. Worker должен экспортировать класс, объявить binding (рекомендуемое имя `TEAM_WORKSPACE`) и добавить **новую** migration с `new_sqlite_classes:["TeamWorkspaceDurableObject"]`, сохранив прежние migrations. Один стабильный `getByName` на командный workspace. Не использовать случайный ID на запрос; не импортировать Node SQLite в Worker.

PUT сравнивает `expectedRevision`, обновляет документ и добавляет запись журнала **в одной синхронной транзакции**. Параллельные публикации одной ревизии дают один успех и 409, без слияния или перезаписи победившей версии. Ошибка вставки журнала откатывает документ и ревизию. Журнал записывается только сервером: ревизия, время, серверная identity/role, число наборов и поручений. API не редактирует и не удаляет журнал. Это история публикаций, не полный diff полей и не криптографически защищённый архив от администратора БД; резервирование и сроки хранения задаёт оператор.

## Ограничение входа и доверенный адрес

12 попыток входа за 60 секунд **на доверенный клиентский адрес**, включая успешные входы. В SQL хранится SHA-256 адреса, не исходный адрес; устаревшие счётчики удаляются, максимум 1024 активных bucket. Дополнительный общий предел — 1200 попыток за минуту. 429 возвращает время ожидания. Политика постоянна при перезапуске процесса/DO, actor и роль никогда не выводятся из IP.

- Node адаптер передаёт только `incoming.socket.remoteAddress` в `clientAddress`. Не доверять X-Forwarded-For/Forwarded. За общим обратным прокси операторы могут иметь общий лимит; это ограничение текущего транспортного контракта.
- Публичный Cloudflare Worker **перезаписывает** `X-Workspace-Client-Address` значением платформенного `CF-Connecting-IP` либо `unknown`, затем передаёт Request через binding. Никогда не копировать одноимённый входящий клиентский header. DO читает только этот внутренний header; сам DO не имеет публичного URL.
- Если адаптер не передал адрес, используется общий `unknown` bucket. Это безопасный отказ, но 12 чужих попыток могут временно блокировать такой общий вход. Для реального размещения нужен также внешний предел нагрузки; IP не является идентификацией человека.

Маршрутизировать только точный `/api/workspace` либо префикс `/api/workspace/` перед другими API; публичные `/api/simulate` и география не требуют новой авторизации. Проверки HTTP/прокси, переписывание внутреннего header и конечный deployment — отдельная ответственность интегратора.

## Панель и ручной обмен

```js
import { mountTeamWorkspace } from './team-workspace.js';
const shared = mountTeamWorkspace(container, {
  getDocument: () => actionRegister.getDocument(),
  applyDocument: (document) => actionRegister.applyDocument(document),
});
// Подключить /team-workspace.css; при размонтировании shared.dispose().
```

При mount проверяется только сессия. До явной публикации локальные данные не отправляются. «Получить общую версию» показывает её ревизию и количество записей, сохраняя локальные правки. Затем пользователь выбирает замену локального реестра или оставляет свой вариант для публикации, отдельно подтверждая полное замещение общей версии. Перед заменой доступно скачивание локальной JSON-копии. Автоматического слияния нет.

`applyDocument` сначала полностью проверяет документ и записывает localStorage; лишь после успеха заменяет отображаемые записи. При ошибке/конфликте локального хранения старый реестр сохраняется. Полученные снимки не активируют создание новых поручений и не считаются свежим расчётом.

409 или неопределённый сетевой исход публикации сохраняет локальную версию и запрещает повторную запись до нового получения общей ревизии. Можно явно оставить локальный вариант после просмотра общей версии. Просмотр журнала доступен отдельно. При 401 нужно войти заново; при 503 панель объясняет отсутствие настройки, не показывает фиктивную активную синхронизацию. Ручные данные не отправляются AI.

## Проверки

```sh
node --test tests/workspace.test.js tests/workspace-panel.test.js tests/action-register-workspace.test.js
```

Для локального **настоящего workerd**, без публикации и реальных секретов, установить `miniflare` и `esbuild` во временный npm prefix и указать абсолютный путь prefix в `WORKSPACE_RUNTIME_DIR`, затем:

```sh
node --test tests/workspace-worker.test.js
```

Если переменной нет, отдельный Worker тест явно пропускается, а не изображает проверку облака. Проверено с Miniflare 5 (его `convertV4MiniflareOptions`), Node 24.19 и актуальным workerd. Тест поднимает SQLite-backed DO, проверяет авторизацию, 200/409 при конкурентной записи, единственную запись аудита, сохранность после dispose/restart, отзыв сессии при смене роли, запрет записи viewer и отзыв cookie после выхода. Это локальная проверка runtime, **не hosted-проверка**.

Автоматические Node проверки дополнительно покрывают отказ при неверной конфигурации, TLS-прокси/Secure-cookie, Origin до чтения тела, отзыв ключа/TTL, подмену роли, точный Content-Type, лимит потокового тела и отказ cancel, SQLite restart, rollback при ошибке audit, изоляцию клиентских rate-limit bucket. DOM-проверки панели покрывают первый upload имеющегося черновика, явное подтверждение замены, конфликт, viewer, поздний ответ после dispose, недоступное localStorage и текстовое отображение потенциального HTML.

Фактическая проверка 23.09.2026: **37/37** Node/DOM/schema-hook тестов и **1/1** отдельный настоящий локальный workerd тест прошли. Worker fixture также перезаписывает внутренний адресный header и проверяет, что его подмена не обходила лимит. Независимый read-only review не нашёл P1 в сервисе/транзакциях; дополнительно проверены 1024 bucket, очистка через 60 секунд и общий предел 1200. Это не проверяет ещё не подключённый production transport.

Изолированный Chromium/Chrome headless: viewport 390×844, document.scrollWidth=390, ошибок страницы нет. Проверены открытие панели и просмотр общей версии; элементы остаются в ширине экрана. Результаты и обычный viewport PNG находятся в локальном временном каталоге `team-workspace-panel-qa` (`browser-evidence.json`, `workspace-390.png`). Стенд использовал подставной transport для визуальной проверки; серверные доказательства получены отдельно тестами выше. Изоляция намеренно не выдаётся за сквозную публичную приёмку.

Перед включением на сайте интегратор повторяет один сквозной сценарий на конечном SHA: локальный расчёт → черновик → вход → просмотр общей версии → публикация → второй клиент → конфликт → обновление → журнал → выход. Нужны отдельно настроенные постоянное хранение, выдача/отзыв операторских ключей, резервирование и проверка транспортных заголовков. В этом PR эти внешние действия не выполняются.

Основания реализации: [Cloudflare transactionSync](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#transactionsync), [Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/), [Node SQLite](https://nodejs.org/api/sqlite.html).
