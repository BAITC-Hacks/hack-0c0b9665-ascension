# Азамату: публикация Telegram-бота с сохранением локального режима

Данияр передал публикацию Азамату 23.09.2026. Цель — работа `@Ascension_City_bot` без включённого компьютера с возможностью вернуться к локальному серверу. Единственный целевой адрес: https://ascension-city-map.azamatbreach.workers.dev.

## Что подготовлено

- Cloudflare Worker передаёт citizen/complaints/webhook API в один `Complaints` Durable Object. Существующие симулятор, AI budget и миграция `v1` сохранены; добавлена `v2-complaints`.
- Общая валидация, приватные квитанции, авторизация панели и обработчик Telegram используются и в Node, и в Worker. Локально сохраняется файловое хранилище, в облаке — отдельные постоянные записи.
- Диалог Telegram сохраняет черновик, шаг меню, подготовленный ответ и факт доставки. Сбой между записью обращения и очисткой черновика обработан через `telegramDraftId`, с регрессионной проверкой. Новое обращение не теряется при позднем повторе старого update.
- Команды `bot:hosted`, `bot:local`, `bot:status` проверяют сервер перед сменой транспорта и не удаляют очередь Telegram. Старый `bot` отказывается запускать polling при активном webhook.

Исходная проверенная база интеграции — `f3885a643c5b2c7d04c452e979673e266d4adb04`. Это **база**, а не готовый hosted-релиз. Точный коммит с этими файлами получает и публикует Git-владелец; при работе используйте переданный им SHA после повторных тестов и dry-run.

## Фактический статус передачи

На компьютере Данияра Cloudflare CLI не авторизован; OAuth ожидание закончилось, после передачи Азамату повторный вход не запускался. Production не изменён, webhook не зарегистрирован, локальный polling не останавливался. В последней read-only проверке Telegram webhook был отключён, очередь пуста.

Проверены автоматические тесты и `wrangler deploy --dry-run`. В настоящем локальном runtime Cloudflare (`wrangler dev --local`) прошли: config, создание синтетического обращения, личная проверка, отказ панели без admin token, список с token, смена статуса и пустая авторизованная webhook-проба без отправки сообщений. Проверка после перезагрузки Worker сохранила обращение и статус. Это не проверка публичного deploy или реального входящего сообщения на хостинге.

## Порядок выпуска

1. Получить от Git-владельца проверенный release SHA, проверить тесты и dry-run именно этого checkout. Параллельную публикацию из `ascension-daniyar` не запускать: обе папки указывают на один Worker.
2. Войти в существующий Cloudflare-аккаунт владельца `azamatbreach`, проверить доступ к `ascension-city-map`. Не создавать новый публичный адрес.
3. Опубликовать код и новую миграцию с сохранением существующих секретов AI. Настроить `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, отдельный `ADMIN_TOKEN`; Telegram token/secret получить у Данияра по приватному каналу. Не помещать их в GitHub/Trello/README. `PUBLIC_BASE_URL` и `TELEGRAM_BOT_USERNAME` находятся в `wrangler.jsonc`.
4. Проверить config с тремя флагами true, защищённость панели и пустую webhook-пробу. До следующего шага бот продолжает работать локально.
5. Завершить миграцию уже принятых реальных обращений по плану ниже. Это обязательный оставшийся пункт перед переключением действующего бота.
6. Согласовать остановку единственного локального polling с Данияром. Зарегистрировать webhook через `npm run bot:hosted`, проверить `bot:status`. Не включать одновременно polling и webhook. В тестовом диалоге проверить меню → обращение → квитанцию → статус в панели; после этого подтвердить работу с выключенным локальным сервером.
7. Передать Данияру release SHA, Cloudflare version ID, ссылку и результат проверок. Ключ панели передать отдельно приватно.

## Перенос существующих обращений — ещё не реализован

На локальном сервере есть действующее хранилище, указанное в `COMPLAINTS_FILE` (у Данияра `var/telegram-complaints.json`). Оно содержит реальное обращение. Текущие CLI-команды базы не синхронизируют. Нельзя считать cutover завершённым, пока исходная квитанция не проверяется на облаке.

Безопасный план для исполнителя:

1. Дать завершить активные диалоги, затем на время снимка остановить локальный polling и запись через локальную панель/форму. Не удалять ожидающие Telegram updates. Сохранить приватную резервную копию действующего файла; синтетические `browser-demo.json` и `.wrangler`-данные не переносить.
2. Сделать одноразовый контролируемый импорт в `Complaints` того же окружения. Импортировать исходные валидированные записи в ключи `complaint:<id>` без регенерации ID, trackingToken, telegramUpdateId, вложений, анализа или истории. Использовать `validateComplaintRecords` и транзакцию, запретить перезапись конфликтующих записей, проверить повторный импорт. Публичного endpoint импорта сейчас нет: его разработка/проверка либо закрытый инструмент миграции остаются работой исполнителя.
3. Сверить число и приватные контрольные суммы записей, проверить старую квитанцию через `/api/complaints/track` и доступ сотрудника к фото/истории, не выводя коды и содержимое в логи.
4. Локальные незавершённые черновики текущего процесса живут в памяти. Их экспорта нет. Перед остановкой согласовать завершение диалогов; если перенос активных черновиков обязателен, сначала реализовать их закрытый экспорт/импорт. Не заявлять, что они автоматически переедут вместе с JSON.
5. Только после проверки переноса выполнить пункт переключения webhook. Сохранить локальную резервную копию. При откате проверить, какие новые обращения появились на хостинге: простое `bot:local` не переносит их обратно.

## Границы интеграции

Ветка Алишера `feat/h12-ui-03-alisher` содержит отдельные demo desk API с SQLite для Node; это отдельная незавершённая адаптация к Worker. Не подменять реальные бот-обращения демонстрационными записями и не объявлять эти кабинеты работающими на Workers только после загрузки HTML. Интеграцию этой ветки ведёт Git-владелец отдельно.

Подробные настройки и команды: [telegram-hosting.md](telegram-hosting.md).
